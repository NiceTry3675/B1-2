# [Analysis] 정상 작업 로그는 FCFS와 부합하는 순차 처리 패턴

## 1. 로그 관찰 개요

보너스 과제로 CPU After의 정상 실행(MEMORY_LIMIT=512, CPU_MAX_OCCUPY=40, MULTI_THREAD_ENABLE=false)을 분석했다. 대상은 **애플리케이션의 작업 실행 순서**이며, 로그만으로 Linux 커널의 스케줄러 알고리즘을 단정하지 않는다.

## 2. 증거 자료

2026-09-05 KST [원본 앱 로그](../evidence/cpu/after/app.log)의 등록 및 시작·완료 순서는 다음과 같다. 같은 로그의 중간 진행률 40/60/80%도 각 작업 안에 연속 배치되어 있다.

| 작업 | 시작 시각 | 완료 시각 | 시작→완료 |
| --- | --- | --- | --- |
| Thread-A | 15:49:44.987 | 15:49:45.194 | 207ms |
| Thread-B | 15:49:45.245 | 15:49:45.451 | 206ms |
| Thread-C | 15:49:45.502 | 15:49:45.709 | 207ms |

등록 로그는 `Registered Tasks: ['Thread-A', 'Thread-B', 'Thread-C']`였다. A 완료 후 B 시작까지 51ms, B 완료 후 C 시작까지 51ms이다. 15:49:45.760에 `All tasks completed.`가 기록되었다.

## 3. 패턴 분석 및 결론

작업이 등록된 A→B→C 순서대로 각각 100%까지 끝난 뒤 다음 작업이 시작되었다. 주어진 FCFS / Round-Robin / Priority 중에서는 **FCFS와 부합하는 비선점 순차 처리**가 가장 자연스러운 추론이다. 관측한 로그에는 미완료 작업 사이를 순환하는 Round-Robin 패턴이 없다. 우선순위 값이나 순서 역전 증거도 없다.

다만 같은 우선순위 작업들의 실행이나 단순 순차 호출도 같은 로그를 만들 수 있다. 한 실행의 출력만으로 내부 알고리즘이 FCFS로 구현되어 있다고 확정할 수 없다. 약 51ms의 로그 간격은 의도적 지연이나 작업 시간이 포함된 값일 수 있으므로 OS time quantum으로 해석하지 않는다.

[ps 원본](../evidence/cpu/after/ps.txt)에서 실제 LWP의 CLS는 `TS`, NI는 10이었다. 이 증거는 앱의 A/B/C 실행 순서와 커널 스케줄링 정책이 서로 다른 층위임을 보여준다. [Linux 스케줄러 공식 문서](https://www.kernel.org/doc/html/latest/scheduler/sched-design-CFS.html)는 실행 가능한 task의 CPU 배분을 설명하며, 애플리케이션 로그의 순차 출력 자체가 커널 FCFS 또는 SCHED_FIFO의 증거는 아니다.

## 4. 장단점과 적합한 서비스

FCFS 방식은 순서가 명확하고 구현이 단순해 작업 순서가 중요한 배치·직렬 처리에 적합하다. 긴 작업이 앞에 오면 짧은 작업까지 기다리는 convoy effect가 발생하므로 응답 지연이 중요한 웹 요청 처리를 모두 하나의 FCFS 대기열로 직렬화하는 데는 불리하다. 그런 서비스에는 작업 분리, 제한된 동시성, 공정한 시간 배분이나 짧은 작업을 별도 처리하는 설계를 고려할 수 있다. 이는 관측된 패턴에 대한 설계적 해석이며 실측 성능 비교 결과는 아니다.
