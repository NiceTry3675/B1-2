# [Runbook] 동시 장애 우선순위와 표준 대응 절차

평가 FAIL #18 보완. 적용 대상은 agent-leak-app의 메모리 보호 종료, CPU Watchdog 종료, 교착상태가 같은 시각에 보고되는 상황이다. 아래 수치·응답 시간은 **이 과제를 위한 운영 판단 기준 제안**이며, 체결된 SLA나 실제 동시 장애 실험 결과가 아니다. 단일 프로세스에서 세 장애가 동시에 재현되었다고 주장하지 않는다.

## 1. 접수와 우선순위 결정

담당자는 최초 알림을 접수하면 시각·서비스·호스트/컨테이너·PID·프로세스 시작 시각·증상을 기록한다. 같은 PID 숫자라도 시작 시각이 다르면 재시작된 별개 실행이다. 종료 전 CPU 알림과 재시작 후 교착 알림을 한 프로세스의 동시 상태로 합치지 않는다. 앱 내부 Heap/Current Load, 프로세스 RSS/CPU, cgroup 및 호스트 사용량도 별도 필드로 기록한다.

**판단 순서: 영향 범위 → 현재 자원 고갈 위험 → 사용자 작업 정지 → 복구까지 남은 시간.** 장애 유형 자체에 고정 순위를 부여하지 않는다.

| 등급 | 판정 기준 | 착수·재판단 목표 |
| --- | --- | --- |
| P0: 확산 위험 | 공용 호스트의 다른 서비스까지 실패하거나, cgroup/호스트 메모리가 계속 증가해 가용 한도 도달 예상이 30초 이내. OOM kill 반복·스왑/메모리 압력도 함께 확인 | 즉시 착수, 1분 이내 담당자 지정·격리 판단. 1분마다 재판단 |
| P1: 서비스 중단 | PID는 있으나 30초 이상 업무 진행이 없고 순환 대기 증거가 있음, 또는 Watchdog/MemoryGuard 종료가 반복되어 요청을 처리할 인스턴스가 없음. 공용 자원 고갈은 없음 | 5분 이내 착수, 15분 이내 임시 복구 또는 복구 지연 사유 기록. 5분마다 재판단 |
| P2: 제한적 영향 | 한 인스턴스가 보호 종료했으나 나머지가 처리 중이고 현재 자원·응답이 안정적이거나, 짧은 CPU burst만 있고 작업은 진행됨 | 30분 이내 분석 착수. 악화하면 즉시 P1/P0로 승격 |

메모리 90% 이상은 조사 트리거다. `memory.max`가 유한한 cgroup에서는 `(memory.max - memory.current) / 최근 증가속도`로 소진 시간을 추정한다. 증가속도가 0 이하이면 이 계산을 사용하지 않는다. 이 추정은 캐시 회수·추가 부하로 달라질 수 있으므로 `memory.events`, 호스트 MemAvailable, 최근 업무 실패를 함께 본다. 앱 MEMORY_LIMIT와 cgroup memory.max를 섞어 계산하지 않는다.

CPU는 **OS 실측 프로세스 CPU가 1코어 기준 90% 이상으로 10초 지속되고 응답/작업 지연이 함께 발생**하면 우선 조사한다. 다중 코어·스레드 환경에서는 코어 수와 cgroup CPU 할당량도 확인한다. 이 값은 앱 Watchdog 임계치가 아니며 앱 내부 Current Load로 대신 판정하지 않는다. 낮은 CPU에서도 서비스가 멈췄으면 P1 판단을 진행한다.

## 2. 동시 알림의 처리 순서

| 동시 관측 상황 | 첫 조치와 그 이유 | 다음 조치 |
| --- | --- | --- |
| 메모리 소진 임박 + CPU 급등 | P0 메모리 발생 인스턴스의 신규 작업 유입을 차단하고 격리. 공용 자원이 소진될 시간부터 확보 | 압력이 내려가면 CPU 실측·Watchdog 로그 확인 후 해당 인스턴스 부하 제한/설정 수정 |
| 교착으로 업무 중단 + CPU burst, 호스트 안정 | P1 교착 인스턴스의 PID·락 로그·스택을 먼저 보존하고 대체 인스턴스로 전환. 짧은 burst만으로 이를 뒤로 미루지 않음 | CPU가 지속 부하인지 확인하고 별도 교정 |
| 교착 + 다른 인스턴스가 호스트 CPU를 지속 독점 | 다른 서비스까지 지연되면 P0 CPU 인스턴스의 유입/실행 자원을 먼저 제한 | 확보된 여유에서 교착 스택 수집·인스턴스 교체 |
| 과거 MemoryGuard 종료 알림 + 현재 교착 | 이미 종료된 PID에 kill을 보내지 않고 해당 로그를 보존. 현재 요청 처리를 막는 교착을 우선 해결 | 새 실행 ID별로 원인을 분리하고 메모리 재발 위험 평가 |

같은 등급이면 영향을 받는 사용자·서비스 수가 큰 사건, 고갈 예상 시간이 짧은 사건, 복구 수단이 없는 사건 순으로 처리한다. 총괄 담당자 한 명이 순서를 기록하고, 추가 담당자가 있으면 다른 인스턴스의 증거 수집을 병행한다. 담당자가 한 명이면 P0 격리 → P1 업무 복구 → 나머지 원인 분석 순서로 진행한다. 한 인스턴스에서 나온 여러 알림이면 실행 ID와 타임라인을 먼저 대조해 중복 대응을 방지한다.

## 3. 표준 운영 절차

### 단계 A. 5초 안에 최소 상태를 확보

실제 작업 자식 PID를 `/proc/PID/exe`와 부모/자식 관계로 확인한다. 아래 명령은 **이미 확인한 PID와 대상 컨테이너 안에서** 실행하며, 출력은 사건별 새 디렉터리에 보존한다. 프로세스 시작 정보도 남겨 PID 재사용을 구분한다.

```bash
# Use the verified workload PID and a new evidence directory.
mkdir -p "$INCIDENT_DIR"
{
date -Iseconds
readlink "/proc/$PID/exe"
ps -p "$PID" -o pid,ppid,lstart,stat,pcpu,rss,args
ps -L -p "$PID" -o pid,lwp,stat,pcpu,rss,wchan:32,comm
cat "/proc/$PID/stat"
cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.events
} > "$INCIDENT_DIR/triage.txt" 2>&1
MONITOR_LOG_FILE="$INCIDENT_DIR/monitor.log" ./monitor.sh "$PID"
```

호스트에서 조회할 때는 `/proc/PID/cgroup`으로 대상 cgroup 경로를 찾는다. 현재 셸의 cgroup을 대상 앱의 것으로 가정하지 않는다. 프로세스가 이미 종료됐으면 남은 앱 로그, 감독 프로세스의 종료 상태, cgroup 카운터를 먼저 보존한다. `-9`/`-15`만으로 OOM Killer 또는 Watchdog를 단정하지 않는다.

### 단계 B. 확산 차단 여부를 먼저 결정

P0에서는 긴 스택 수집을 기다리지 않는다. 가능한 최소 로그를 남긴 뒤 문제 인스턴스의 신규 요청/작업 유입을 차단하고 정상 인스턴스로 전환한다. 여유가 없으면 확인한 대상 프로세스를 중단해 자원부터 회수한다. P1/P2이고 자원이 안정적이면 앱 로그 복사, 5초 간격 ps/top, 1초 관제와 스택 등 증거를 먼저 확보한다. 증거 확보 지연이 위험해 중단했다면 생략한 자료와 이유를 기록한다.

### 단계 C. 유형별 증거와 임시 조치

| 유형 | 종료·재시작 전 핵심 증거 | 조치 |
| --- | --- | --- |
| MemoryGuard | RSS 증가, Memory limit exceeded, SELF-TERMINATED, 감독 프로세스 종료 상태, memory.events | 용량 여유를 확인한 뒤 MEMORY_LIMIT=512로 재실행. 100→200은 지연에 그쳤고 512에서는 정리를 관측했다는 기존 실험 결과를 적용 |
| CPU Watchdog | 대상 PID의 OS CPU 시계열, Current Load 별도 기록, WATCHDOG SIGTERM 로그 | CPU_MAX_OCCUPY=40으로 재실행하고 cooldown 확인. 필요하면 유입 제한; CPU 상한 조정만으로 코드 결함이 해결됐다고 판단하지 않음 |
| Deadlock | PID·LWP, 마지막 락 보유/대기 로그, GDB 전체 스레드 bt, strace futex/write | 증거 확보 후 MULTI_THREAD_ENABLE=false로 교체 실행. 기존 멈춘 프로세스에 export만 해서는 설정이 반영되지 않음 |

교착 진단은 [직접 증거 및 수집 절차](deadlock.md)의 `scripts/capture_deadlock.py`를 격리된 재현 환경에서 사용한다. GDB attach는 앱을 잠깐 멈추므로 원인 분류 시 부작용을 기록한다. `strace`를 detach한 뒤 GDB를 붙인다. 이 수집 때문에 P0 격리를 지연하지 않는다.

### 단계 D. 종료·재시작·재부팅의 선택

정상 인스턴스로 전환한 뒤 확인한 대상에 SIGTERM을 보내고 **5초 동안** 종료·PID·포트 상태를 확인한다. 남아 있으면 실행 파일과 저장한 시작 식별자가 같은 대상인지 다시 확인한 뒤 해당 PID에만 SIGKILL을 사용한다. 이름 전체를 대상으로 하는 `pkill`, 공용 호스트 전체 재부팅은 기본 대응으로 삼지 않는다. SIGKILL은 정리 핸들러를 건너뛰므로 미완료 작업의 재처리 여부를 기록한다.

프로세스가 사라지고 15034 포트가 해제된 후 기존 필수 경로·키·권한을 유지하며 MEMORY_LIMIT=512, CPU_MAX_OCCUPY=40, MULTI_THREAD_ENABLE=false로 **새 프로세스**를 시작한다. 시작 시각과 새 PID를 별도로 기록한다. 이 조합은 기존 정상 경로 관측에 근거한 임시 설정이며 모든 환경의 무장애 보장이 아니다.

재부팅은 프로세스 종료나 컨테이너 교체로 복구되지 않고 호스트 자체가 응답하지 않아 서비스 복구가 불가능한 경우의 마지막 수단이다. 가능한 증거·시각·실패한 복구 시도·재부팅 판단 이유를 남긴다. 앱 한 개의 교착이나 자체 보호 종료만으로 호스트를 재부팅하지 않는다.

## 4. 복구 확인과 종료 기준

담당자는 새 PID 존재와 포트 LISTEN만으로 복구를 선언하지 않는다. 다음 항목을 **최소 3분** 확인한 뒤 결과를 사건 기록에 남긴다. 이 기간은 제안된 운영 검증 절차이며 이번 보완에서 3분 복구 실험을 추가했다는 뜻이 아니다.

- 대표 업무/테스트 작업이 실제 완료되고 로그가 계속 증가한다. Scheduler의 작업 완료와 이후 워커 진행을 확인한다.
- Memory Cache Flushed 후 RSS 감소, CPU cooldown 진입·복귀가 확인되고 새 MemoryGuard/Watchdog 종료가 없다. 주기가 길어 정리·cooldown이 아직 없으면 관측을 연장한다.
- 두 번 이상의 자원 정리 주기 및 CPU 부하 주기를 확인하고, cgroup OOM 카운터와 공용 호스트의 다른 서비스가 안정적이다.
- BLOCKED 로그와 동일 자원의 순환 대기가 재발하지 않으며, 실제 사용자 영향이 해소되었다. 단순 futex_wait 하나는 교착 재발 근거로 쓰지 않는다.

재발하면 사건을 닫지 않고 해당 인스턴스를 다시 격리하고 P0/P1 기준을 재평가한다. 반복 재시작으로 증거를 덮어쓰지 않는다. 이미 안정성이 확인된 대체 인스턴스를 유지하고, 변경한 설정·부하 조건을 개발 담당자에게 인계한다.

사건 기록에는 **접수 시각, 실행 ID, 동시 알림 목록, 우선순위와 선택 근거, 자원 고갈 예상, 증거 경로, 조치 담당자·시각, 보낸 신호와 주체, 변경 설정, 새 PID, 업무 완료·관제 Before/After, 재발 여부, 후속 코드 수정 담당자**를 포함한다. 종료 전 총괄 담당자가 누락과 복구 기준 충족을 확인한다.
